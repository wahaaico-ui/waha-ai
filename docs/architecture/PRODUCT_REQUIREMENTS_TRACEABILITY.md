# WAHA — مصفوفة المطابقة الرسمية بين الرؤية والمنتج الحالي

**الإصدار:** 1.0  
**تاريخ التدقيق:** 2026-08-26  
**مرجع المنتج:** `الواحة_وثيقة_المنتج_الرسمية_الإصدار_الثاني.pdf` (61 صفحة)  
**مرجع التنفيذ:** المخطط، المسارات، واجهات API، والمكوّنات الموجودة في المستودع الحالي.

> هذه الوثيقة مرجع قرار معماري، وليست ادعاء اكتمال. لا يُصنَّف بند بأنه مكتمل إلا إذا وُجد دليل مباشر في المسار الفعّال للمستخدم.

## مفتاح الحالة

| الحالة | المعنى |
|---|---|
| 🟢 مكتمل | السلوك المطلوب موجود في المسار الفعّال وله دليل مباشر |
| 🟡 جزئي | توجد بنية أو واجهة قابلة لإعادة الاستخدام، لكن الوعد الكامل غير منفذ |
| 🔴 مفقود | لم يوجد تنفيذ فعّال بعد الفحص |
| ⚠️ متعارض | التنفيذ الحالي يناقض مبدأً صريحًا في وثيقة المنتج أو يعرّض الاتساق للخطر |
| ⚪ خلفي فقط | يوجد API أو كود، لكنه غير موصول برحلة المستخدم الفعّالة |

## 1. الحقيقة التنفيذية المختصرة

| المجال | الحالة | الحقيقة الحالية | القرار |
|---|---:|---|---|
| الحاوية البحثية | 🟢 | `projects` هي الحاوية الرئيسية، ومخرجات الرحلة محفوظة في `documents` مرتبطة بـ `project_id` | الإبقاء عليها كأساس |
| الرحلة الفعّالة | 🟡 | 8 مراحل: استكشاف، عنوان، مشكلة/فجوة، أهداف، أسئلة، منهجية، أدبيات، تحليل أدبيات | توسيعها تدريجيًا؛ لا ادعاء وصولها إلى النشر |
| بوابات الانتقال | 🟡 | تمنع القفز بناءً على وجود المخرجات وشروط بنيوية محدودة | لا تُسمّى Consistency Engine |
| Research Objects | 🔴 | لا يوجد Domain Model موحد للعناصر البحثية | بناء طبقة قراءة مشتركة أولًا بلا migration |
| Consistency Engine | 🔴 | لا يوجد تقييم دلالي موحّد للعلاقات بين العناصر | أول فحص حقيقي: Problem ↔ Objectives |
| Workspace مقابل Journey | 🟡 | واجهتان متداخلتان جزئيًا فوق `projectId` وبيانات غير موحدة بالكامل | الإبقاء على الواجهتين وبناء Domain Model مشترك تحتهما |
| البحث الأكاديمي الموحد | 🟢 | Registry ومحرك موحد وتوجيه وتطبيع ودمج وإزالة تكرار موجودة | اعتماد المحرك الموحد كممر وحيد للأدلة |
| التحقق الأولي من الفكرة | ⚠️ | يستدعي بعض المصادر مباشرة ويكرر تخزين الفكرة في أكثر من شكل | توحيد القراءة والكتابة لاحقًا دون فقد بيانات |

## 2. البنية العامة والذاكرة

| متطلب الوثيقة | الحالة | الدليل الحالي | الفجوة/معيار القبول |
|---|---:|---|---|
| مشروع بحثي موحد | 🟢 | جدول `projects` وملكية خادمية للمشروع | لا تغيير معماري جذري |
| حفظ مخرجات المراحل | 🟢 | `documents` بأنواع `journey:*` وإصدارات متزايدة | الاستمرار مع توثيق الأنواع |
| منع القفز | 🟡 | `/api/projects/[projectId]/journey` يحسب المرحلة التالية المسموحة | يلزم قرار نوعي مبني على الاتساق، لا مجرد اكتمال الحقول |
| سجل إصدارات كامل | 🟡 | الخادم يزيد `version` عند كل عملية اعتماد | لا توجد واجهة قائمة إصدارات كاملة للمستخدم |
| استعادة نسخة سابقة | 🔴 | لا يوجد مسار أو واجهة Restore مثبتة | يلزم API آمن + سجل قرار + UI |
| حفظ تلقائي لكل تغيير | 🔴 | الصفحات تعتمد أزرار اعتماد/حفظ صريحة | لا يجوز وصفه Autosave حاليًا |
| استقبال ذكي عند العودة | 🟡 | صفحة الرحلة تعرض الاسم، آخر نشاط، معاينة، والخطوة التالية | لا يوجد رقم جلسة فريد ولا استعادة آخر مسودة غير معتمدة بالكامل |
| إرسال نسخة احتياطية بالبريد | 🔴 | غير موجود في الرحلة الفعالة | يحتاج سياسة أحداث بريدية وموافقة المستخدم |
| مصدر حقيقة واحد للفكرة | ⚠️ | `idea_verifications` و`idea_verification` و`journey:verify` قد تمثل الفكرة نفسها | تعريف سجل Canonical وطبقة توافق للقديم |

## 4. المحور الثاني — التحقق من الفكرة

| المتطلب | الحالة | الدليل الحالي | الفجوة |
|---|---:|---|---|
| بحث بمصادر حقيقية | 🟢 | نتائج فعلية من مصادر أكاديمية، ولا تُنشأ مراجع وهمية داخل المسار الحالي | توحيد المسار عبر UnifiedResearchEngine |
| عدد الدراسات والتوزيع الزمني والجغرافي والمنهجي | 🟡 | API يحسب `yearDist` و`geoDist` و`methodDist` ويعرض الأدلة | الانتماء المؤسسي للمؤلف لا يساوي بلد تنفيذ الدراسة؛ يجب إبقاء التنبيه |
| درجة شفافة من 100 | 🟡 | `computeScore` حتمي بأوزان 25/20/20/15/10/10، والواجهة تعرض التفصيل | الاسم الصحيح «مؤشر استدلالي» لا «احتمال قبول» |
| قرار أقل من 30 / تحسين / متابعة | 🟢 | `makeDecision` يطبّق الحدود، مع شرط أدلة لا يقل عن 3 للمتابعة | توثيق نسخة المعادلة داخل الناتج |
| اتساق الدرجة مع معناها | ⚠️ | بند `consistency` محسوب من متوسط الاستشهادات، وغياب النتائج قد يمنح نقاط فجوة | إعادة تسمية المكوّنات ومنع دقة مضللة |
| بصمة فكرة وتنبيه تشابه خاص | 🔴 | لا نموذج Fingerprint مثبت | يحتاج تصميم خصوصية وعدم كشف هوية |
| مؤشر توقيت: مشبعة/ذروة/صاعدة | 🟡 | يمكن استنتاجه جزئيًا من التوزيع الزمني | لا يوجد نموذج توقيت مُعاير ومختبر |
| وسوم المعرفة | 🟡 | `EvidenceBadge` يميّز موثق/استنتاج/اقتراح في صفحة التحقق | غير إلزامي على كل مخرج، ووسم «معلومة عامة تحتاج تحقق» غير مطبق بصورة موحدة |

### حقيقة معادلة التحقق الحالية

```text
وجود فجوة محتملة        25
حداثة الأدلة             20
تنوع المناهج             20
التنوع الجغرافي          15
كفاية المراجع            10
إشارة الاستشهادات        10
المجموع                 100
```

هذه معادلة برمجية فعلية وليست نصًا مولدًا، لكنها **Heuristic** وليست احتمال قبول علمي أو ضمان جدة. يجب تخزين `formulaVersion` وشرح حدودها للمستخدم.

## 5. المحور الثالث — التبلور والاتساق

| المتطلب | الحالة | الدليل الحالي | الفجوة |
|---|---:|---|---|
| صياغة/مقارنة العنوان | 🟡 | مرحلة عنوان فعالة ومقارنة خيارات | لا تقييم دلالي مُعاير بحد عبور 70 كما تصفه الوثيقة |
| المشكلة والفجوة | 🟡 | مرحلة موحدة تحفظ المشكلة والفجوة | الفجوة ليست Research Object مستقلًا، والتحقق بنيوي غالبًا |
| الأهداف | 🟡 | قائمة أهداف محفوظة | لا IDs مستقرة ولا تتبع مباشر لأي جزء من المشكلة |
| الأسئلة | 🟡 | قائمة أسئلة محفوظة | لا خريطة صريحة سؤال→هدف |
| الفرضيات | 🔴 | لا مرحلة أو نموذج فعّال مستقل | غير موجود |
| المنهجية | 🟡 | مرحلة منهجية فعالة | المجتمع والعينة والمتغيرات والأداة مدمجة وليست Objects قابلة للفحص |
| Problem ↔ Objectives | 🔴 | لا تقييم علاقة دلالية فعلي | أول فحص مطلوب في Consistency Engine |
| Objectives ↔ Questions | 🔴 | لا تقييم تغطية أو تعارض | غير موجود |
| Questions ↔ Hypotheses | 🔴 | الفرضيات نفسها غائبة | غير موجود |
| Questions ↔ Methodology | 🔴 | لا ملاءمة دلالية قابلة للتفسير | غير موجود |
| Variables ↔ Instrument | 🔴 | لا Objects للمتغيرات/الأداة | غير موجود |
| Methodology ↔ Analysis | 🔴 | التحليل الحالي تحليل أدبيات، لا خطة تحليل بيانات | غير موجود |
| Results ↔ Questions | 🔴 | النتائج ليست مرحلة فعالة | غير موجود |
| خريطة اتساق مرئية | 🔴 | مؤشر تقدم خطي فقط | لا تخلط Progress مع Consistency |
| ثلاثة محكمين افتراضيين | 🔴 | لا تنفيذ في المسار الفعّال | بعض المسارات القديمة/المؤرشفة لا تُعد ميزة منتج فعالة |

## 6. المحور الرابع — البناء والكتابة

| المتطلب | الحالة | الدليل الحالي | الفجوة |
|---|---:|---|---|
| اختبار أسلوب إلزامي | 🔴 | غير موجود في الرحلة الفعالة | غير موجود |
| محرر يتحدى التفكير ولا يكتب بدل الباحث | ⚠️ | `ResearchDraftAssistant` يطلب من `/api/research/draft` مسودة كاملة ويملأ الحقول | تعارض مباشر يحتاج قرار منتجي قبل توسيعه |
| إبراز صوت الباحث | 🟡 | مرحلة المشكلة تطلب رأي الباحث وسبب الأهمية | يلزم فصل مساهمة الباحث عن النص المقترح وتوثيق أصل كل فقرة |
| الإطار النظري والنتائج والمناقشة والخلاصة والتوصيات | 🔴 | لا مراحل فعالة كاملة | غير موجود |
| أنماط المشرف | 🔴 | لا تنفيذ فعّال | غير موجود |

**قرار إلزامي قبل بناء Research Objects:** كل نص مقترح آليًا يجب أن يحمل `origin = ai_draft` وألا يصبح معتمدًا دون تحرير/قرار موثق من الباحث. الخيار الأكثر التزامًا بالوثيقة هو تحويل المساعد من «مسودة جاهزة» إلى «هيكل، أسئلة تحدٍّ، ونواقص قابلة للإجابة».

## 12. مواءمة Research Objects

| الواقع الحالي | Research Object المقترح | إعادة الاستخدام | الحاجة إلى Migration الآن |
|---|---|---|---:|
| `journey:verify` | Idea / Topic | نعم عبر Adapter للقراءة | لا |
| `journey:title` | Topic / Title | نعم | لا |
| `journey:problem` | Problem + Gap | نعم مع فصل منطقي مؤقت | لا |
| `journey:objectives` | Objective[] | نعم مع IDs مشتقة ثابتة مؤقتًا | لا |
| `journey:questions` | ResearchQuestion[] | نعم | لا |
| `journey:methodology` | Methodology + Population + Sample + Instrument | جزئي؛ يحتاج parsing محافظ | لا في المرحلة الأولى |
| أوراق المكتبة/نتائج البحث | Paper / Evidence | نعم | لا |
| citations | Citation / EvidenceLink | نعم جزئيًا | لا |

**قرار المعمارية:** الخيار D — إنشاء Research Object Domain Model مشترك تحت Journey وWorkspace، دون دمج الواجهتين ودون إنشاء جداول جديدة في أول خطوة.

## 13. القرارات الثلاثة التي حُسمت بالفحص

1. **وسوم الثقة:** موجودة جزئيًا في `verify-idea`، وليست سياسة منصة عامة. يجب أن يكون `knowledgeType` إلزاميًا في عقد Research Object بالقيم: `documented | inference | suggestion | general_unverified`.
2. **درجة التحقق:** خوارزمية حتمية فعلية وليست AI، لكنها مؤشر استدلالي يحتاج اسمًا صحيحًا و`formulaVersion` وحدودًا معلنة.
3. **المحرر الأكاديمي:** يولّد مسودات كاملة حاليًا؛ هذا تعارض مثبت مع مبدأ «التحدي لا الكتابة بالنيابة». لا يُوسّع قبل قرار منتجي وتصحيح أصل المحتوى.

## 14. المخاطر قبل أي Migration

| الخطر | المستوى | المعالجة المطلوبة |
|---|---:|---|
| إنشاء جدول Research Objects فورًا يكرر `documents` | عالٍ | Adapter قراءة فقط أولًا |
| فصل المشكلة والفجوة بصورة تفقد المحتوى القديم | عالٍ | mapping غير هدّام + fixtures من مشاريع حقيقية منزوعة الهوية |
| تغيير أنواع Documents يكسر الرحلة الحالية | عالٍ | Backwards compatibility وإبقاء `journey:*` |
| تحويل الدرجة الحالية إلى «احتمال» | عالٍ | تغيير المصطلح وتوثيق المعادلة |
| اعتبار النص المولد مساهمة الباحث | عالٍ | حقل origin + اعتماد صريح + سجل مراجعة |
| ربط Evidence بمخرجات غير مستقرة | متوسط | stable object IDs في طبقة العرض قبل DB migration |

## 15. نتيجة المرحلة الأولى

المصفوفة المرفقة **صالحة كأساس بعد هذه التصحيحات، وليست صالحة للاعتماد بنسختها الأصلية**. الواقع الحالي يملك نواة قوية للمشاريع، الحماية، البحث الأكاديمي، والحفظ المرحلي؛ لكنه لا يملك حتى الآن Research Consistency Engine بالمعنى المعلن في الوثيقة.

### أول خطوة تنفيذية تالية فقط

إنشاء عقد TypeScript للقراءة فقط باسم مفاهيمي مثل `ResearchObjectView` مع Adapter يحوّل أحدث `journey:*` Documents إلى Objects مؤقتة، ثم اختبار Mapping على:

```text
Problem → Objective[]
```

لا Migration، لا كتابة مزدوجة، ولا تغيير واجهة في تلك الخطوة. بعد ثبات العقد، يُبنى أول تقييم دلالي قابل للتفسير `Problem ↔ Objectives` مع أدلة ونتائج تحقق وسجل إصدار.
